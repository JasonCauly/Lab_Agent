项目逻辑检查报告（2026-10-20）

本轮检查覆盖登录与用户管理、实验室与设备管理、预约和文件上传。以下列出当前仍存在的问题及处理建议，业务代码在本轮检查中未作修改。

验证方式：源码检查、隔离 SQLite 数据库中的行为复现、受控并发请求复现、Vue 组件脚本与项目实际使用的表单校验器验证。测试使用合成数据，不连接项目现有 MySQL 数据库。并发结果说明当前代码缺少原子性保证；实际部署数据库的约束和并发负载仍需进一步验证。前端验证为组件脚本和校验逻辑验证，未覆盖浏览器完整操作流程。

P1 表示优先处理的数据一致性或核心流程问题；P2 表示常见操作失败或访问控制、会话处理问题；P3 表示功能或界面行为不一致。

1. **[P1] 同一资源、同一时间的并发预约可以同时成功。**

   位置：[reservation_service.py](../backend/app/services/reservation_service.py)，第 45–72 行。

   当前先查询冲突，再插入预约；两步之间没有锁或数据库级的时段占用保证。隔离测试让两个请求都完成“无冲突”检查后再提交，同一实验室、同一日期、同一时段最终保存了两条预约。

   建议：按预约资源加事务锁，并在锁内重新检查重叠后写入；所有相关预约入口使用相同的锁规则。只给完全相同的开始、结束时间加唯一约束，无法阻止部分重叠的时段。

2. **[P1] 预约接口允许把其他实验室的设备挂到当前实验室。**

   位置：[reservation_service.py](../backend/app/services/reservation_service.py)，第 35–46 行。

   当前只检查设备是否存在、是否维修，没有检查 `equipment.lab_id == data.lab_id`。测试成功提交了“A 实验室 + B 实验室设备”，保存后的预约归属与设备实际归属不同；冲突检查又包含提交的实验室 ID，因而可能漏掉设备真实所属实验室中的预约。

   建议：后端校验设备归属；设备预约的冲突检查应围绕实际资源进行，不能依赖未经验证的实验室 ID。

3. **[P1] 设备更换所属实验室后，可以绕过原有预约。**

   位置：[equipment_service.py](../backend/app/services/equipment_service.py)，第 67–95 行；[reservation_service.py](../backend/app/services/reservation_service.py)，第 45–55 行。

   管理员可以直接修改设备的 `lab_id`，已有预约仍保留旧的实验室 ID。测试先在 B 实验室预约设备，再把设备转移到 A 实验室，随后同一设备、同一时段的新预约也成功，形成两条重叠记录。

   建议：转移前处理尚未结束的有效预约，或明确禁止带有未来有效预约的设备转移；历史预约的原实验室信息应保留。设备冲突校验也应覆盖转移前的记录。

4. **[P1] 预约流程只有提交，没有查询、审核和取消。**

   位置：[api/reservation.py](../backend/app/api/reservation.py)，第 14 行；[reservation_service.py](../backend/app/services/reservation_service.py)，第 69 行。

   路由检查确认预约模块目前仅有一个 POST 接口。每次提交均写入 `status=0`，前端提示等待审核，但没有管理员审核、用户查看和取消预约的正常操作入口。待审核记录会继续参与时段冲突判断。

   建议：补齐用户自己的预约查询和取消、管理员审核及相应页面；同时定义审核、拒绝、取消的权限和状态转换规则。

5. **[P1] 并发注册可以创建同名账号。**

   位置：[auth_service.py](../backend/app/services/auth_service.py)，第 25–42 行；[models/user.py](../backend/app/models/user.py)，第 10 行。

   注册仅通过“先查询是否存在”避免重复，模型没有声明用户名唯一约束。受控并发测试中，两个同名注册请求都成功，数据库出现两条同名用户；登录使用 `.first()`，会造成账号身份和密码匹配结果不明确。

   建议：数据库对用户名增加唯一约束，并将并发插入冲突转成“账号已存在”的业务提示。对现有数据库加约束前，先检查并处理已有重复数据。

6. **[P2] 无效日期和零时长预约可以保存。**

   位置：[schemas/reservation.py](../backend/app/schemas/reservation.py)，第 8 行；[reservation_service.py](../backend/app/services/reservation_service.py)，第 18–22 行。

   预约日期是未经日期格式校验的字符串，只做字符串大小比较；结束时间仅禁止小于开始时间。测试中，`2099-99-99` 被写入数据库，`09:00–09:00` 也提交成功。

   建议：使用日期类型或严格解析日期，禁止结束时间小于或等于开始时间；ID 使用正整数约束。前端也应提供相同的即时校验。

7. **[P2] 实验室和设备的基础数据缺少后端业务校验。**

   位置：[schemas/lab.py](../backend/app/schemas/lab.py)，第 18–36 行；[schemas/equipment.py](../backend/app/schemas/equipment.py)，第 18–35 行。

   测试可保存负容量、负设备数量、设备状态 `9`，以及格式为 `invalid` 的开放时间。后者在提交预约时进入 `datetime.strptime()`，直接抛出异常。开始开放时间晚于结束时间也没有保存前的校验。

   建议：为容量和数量设置合理范围，为状态和角色限定枚举，为开放时间做格式及先后顺序校验；更新接口也执行同样规则。仅依赖前端控件不足以保护接口数据。

8. **[P2] 新增设备会继承上一次编辑的设备数据。**

   位置：[Equipment.vue](../frontend/src/views/Equipment.vue)，第 216–227 行。

   `resetForm()` 仍使用实验室字段，未重置 `lab_id`、`spec`、`quantity`，并把整数设备状态重置成布尔值 `true`。组件脚本测试中，编辑一条型号 MSP430、数量 49 的设备后点击新增，新表单仍带有原实验室、型号和数量；状态类型也与单选项的 `1/0` 不一致。

   建议：按设备表单实际字段重置全部值，设备状态统一使用 `1/0`。

9. **[P2] 手动修改实验室容量后，表单可能无法提交。**

   位置：[Lab.vue](../frontend/src/views/Lab.vue)，第 103–104 行及第 191–194 行。

   容量使用 `el-input`，用户输入后得到字符串；校验规则却要求 `integer`。用项目实际校验器验证，输入值 `"30"` 被拒绝，即使它是合法的正整数文本。

   建议：改用 `el-input-number`，或在进入校验前转换为数值；后端仍保留正整数约束。

10. **[P2] 删除有预约记录的用户仍会触发外键异常。**

    位置：[user_service.py](../backend/app/services/user_service.py)，第 99–109 行；[User.vue](../frontend/src/views/User.vue)，第 241 行。

    用户删除逻辑仍直接执行数据库删除，缺少实验室、设备删除现已具备的关联检查和回滚处理。隔离测试中删除有预约记录的用户触发 `IntegrityError`。此外，用户删除确认框没有捕获 Promise 拒绝；测试确认点击取消也会出现未捕获拒绝。

    建议：有预约历史的用户采用禁用或明确的禁止删除提示，保留历史归属；前端捕获取消和请求异常。

11. **[P2] JWT 有效期存在本地时间与 UTC 混用。**

    位置：[utils/jwt.py](../backend/app/utils/jwt.py)，第 15–17 行。

    生成过期时间使用不含时区的本地 `datetime.now()`。在当前 UTC+8 环境中，隔离测试设置有效期 24 小时，生成令牌距离实际过期约 32 小时，偏差约 8 小时。

    建议：使用带 UTC 时区的当前时间计算 JWT 过期时间，并测试令牌实际剩余有效期与配置一致。

12. **[P2] 修改密码不会使旧令牌失效。**

    位置：[user_service.py](../backend/app/services/user_service.py)，第 32–39 行；[dependencies/auth.py](../backend/app/dependencies/auth.py)，第 19–31 行。

    改密只更新密码哈希；认证只检查令牌、用户存在及禁用状态。测试中，改密前取得的令牌在改密后仍可通过 `get_current_user()`。当前页面退出只是清除本地存储，其他客户端持有的旧令牌仍可使用到过期。

    建议：明确改密后的会话策略；如需退出旧会话，使用令牌版本或会话失效时间等服务器端校验机制。

13. **[P2] 唯一管理员可以把自己降级或禁用。**

    位置：[user_service.py](../backend/app/services/user_service.py)，第 86–95 行。

    删除接口禁止删除本人，但更新接口没有对应保护。测试可把唯一管理员的角色改为学生，数据库中管理员数量变为 0，此后无法通过正常管理界面恢复管理员。

    建议：至少保护最后一个有效管理员，防止其被降级或禁用；明确管理员自我修改角色和状态的规则。

14. **[P2] 文件上传接口没有登录校验。**

    位置：[api/files.py](../backend/app/api/files.py)，第 18–19 行。

    路由依赖检查确认上传接口没有认证依赖，所属 API 路由也没有统一认证依赖。未登录请求可以使用上传接口写入服务器目录，当前配置允许单文件最高 100 MB。

    建议：为上传接口增加登录身份校验，并按头像、封面等实际用途限制文件类型和大小。本轮只检查依赖声明，没有向现有上传目录写入文件。

15. **[P2] 超过 bcrypt 支持字节数的密码会导致异常。**

    位置：[utils/password.py](../backend/app/utils/password.py)，第 7、13 行；[schemas/auth.py](../backend/app/schemas/auth.py)。

    当前 bcrypt 5 对超过 72 字节的密码抛出 `ValueError`，注册和密码修改的后端请求模型没有对应长度限制。测试 73 个 ASCII 字符即可触发异常；中文密码应按 UTF-8 字节数计算。

    建议：在调用密码哈希和验证函数前统一校验允许的密码字节长度，并返回清晰的参数提示；保持注册、登录、改密和管理员创建用户的规则一致。

16. **[P3] 设备搜索提示支持型号，后端实际只搜索名称。**

    位置：[Equipment.vue](../frontend/src/views/Equipment.vue)，第 26 行；[equipment_service.py](../backend/app/services/equipment_service.py)，第 28–29 行。

    测试设备名称为 Graphics workstation、型号为 RTX4090，按 RTX4090 查询结果为 0。前端提示“请输入设备名称或型号”与实际行为不一致。

    建议：查询同时匹配 `name` 和 `spec`，或调整输入框提示以匹配实际功能。

17. **[P3] 按关闭状态筛选实验室时，条件被忽略。**

    位置：[lab_service.py](../backend/app/services/lab_service.py)，第 45 行。

    使用 `if status:` 判断是否追加筛选，导致传入 `False` 时跳过条件。测试查询关闭实验室时，同时返回开启和关闭的实验室。

    建议：用 `status is not None` 判断是否传入筛选值。

18. **[P3] 编辑用户时，状态类型与单选控件不一致。**

    位置：[User.vue](../frontend/src/views/User.vue)，第 122–123、233 行；[schemas/user.py](../backend/app/schemas/user.py)，第 18 行。

    接口返回布尔状态，编辑时直接赋给表单，但单选项使用数值 `1/0`。组件验证确认绑定值是布尔值，与单选项类型不同，可能出现已有状态未选中的表现。

    建议：前后端统一使用布尔值，或在进入表单时明确转换为 `1/0`。

还需要明确两项业务规则：

- **整间实验室预约与该实验室内的设备预约是否互斥。** 当前代码只分别检查“实验室预约”或“同一设备预约”，测试中整间实验室与其中设备在同一时段均可预约。如果整间预约应占用全部设备，则需要双向冲突检查。
- **设备数量表示库存，还是整组设备作为一个资源。** 当前 `quantity` 仅展示，预约没有数量参数，也不计算剩余可用数量；一条设备记录一旦被预约，整条记录对应的数量都会被排斥在同一时段之外。如果要预约其中若干台，需要数量和时段库存规则。

建议处理顺序：先解决预约并发、设备归属及转移问题和账号唯一性，再补预约查询、审核、取消流程；随后修复管理表单、删除用户、后端输入校验以及会话和上传权限问题。涉及整间实验室与设备互斥、设备数量的部分，先确定业务规则再实现。
